# 실험 설계: 임베딩 3종 x Vector DB 2종

`Structure.md` 6.1의 "임베딩 모델"과 "Vector DB" 두 칸을 근거를 갖고 채우기 위한 실험입니다.
두 항목 모두 **나중에 바꾸면 전체 재적재**가 필요해(리스크 표, 박찬영) 초반에 확정해야 합니다.

## 1. 무엇을 통제하고 무엇을 바꾸는가

| 구분 | 내용 |
| --- | --- |
| 고정 | FAQ 100건, 평가 질문 30건, 청크 전략(FAQ 1건 = 1청크), 거리 함수(코사인), HNSW(m=16, ef_construct=64) |
| 변수 1 | 임베딩 모델 3종 |
| 변수 2 | Vector DB 2종 |

**공정성 장치**
- 문서 임베딩은 모델당 한 번만 계산해 `results/embeddings_*.npz` 에 캐시하고, pgvector 와 Qdrant 가 **같은 벡터**를 받습니다. 그래야 두 DB 사이 차이가 순수하게 DB 차이입니다.
- 질의 임베딩도 모델당 한 번 계산해 두 스토어가 공유합니다.
- e5 계열은 `query:` / `passage:` 접두어를 붙여야 제 성능이 납니다. nomic 은 `search_query:` / `search_document:` 를 씁니다. 접두어를 빼고 비교하면 e5 가 부당하게 낮게 나오므로 `config.EMBED_MODELS` 에 모델별로 명시했습니다.

## 2. 검색 방식과 임베딩 대상 텍스트

검색은 **밀집 벡터 단독**입니다(Structure.md 5.5 의 P0). 하이브리드(BM25)와 Reranker 는 P2 로 두고 이번 범위에서 뺐습니다.

| 단계 | 내용 |
| --- | --- |
| 청킹 | FAQ 1건 = 1청크. 분할하지 않음 |
| 유사도 | 코사인 (pgvector `1 - (v <=> q)`, Qdrant `Distance.COSINE`) |
| 검색 | top-k 최근접 (서비스 기본 3, 평가 5) |
| 후처리 | 최고 유사도가 임계값 미만이면 LLM 을 호출하지 않음 (FR-B7) |

두 스토어의 점수 스케일을 코사인 유사도로 맞춰야 임계값 하나를 공통으로 쓸 수 있습니다.


`[카테고리] 질문 + 개행 + 답변` 을 한 덩어리로 임베딩합니다(`app/ingest.py: doc_text`).
질문만 임베딩하면 사용자가 답변 쪽 표현(예: "위약금" 대신 "할인반환금")으로 물었을 때 놓칩니다.

## 3. 지표

| 지표 | 의미 | 기준 |
| --- | --- | --- |
| Recall@1 | 1순위가 정답 FAQ인 비율 | 참고용 |
| **Recall@3** | 상위 3건 안에 정답이 있는 비율 | **NFR-3.2: 80% 이상** |
| Recall@5 | 상위 5건 안에 정답이 있는 비율 | top-k 확대 효과 확인 |
| MRR@5 | 정답의 평균 역순위 | 순위 품질 |
| 검색 지연 평균/p95 | 벡터 검색만의 시간 | NFR-1.1: 500ms 이내 |
| 질의 임베딩 지연 | 질문 1건 임베딩 시간 | CPU 환경의 실제 병목 |

정답(gold)은 질문당 1~2개를 허용합니다. FAQ 100건 안에는 정답이 될 수 있는 항목이 둘 이상인 질문이 실제로 존재하기 때문입니다(예: "집에서 해지되나요" → FAQ-041, FAQ-051).

## 4. 판단 기준 (실험 전에 정해둔다)

실험 후에 기준을 만들면 원하는 결론에 맞추게 됩니다. 먼저 적어 둡니다.

**임베딩 모델**
1. Recall@3 이 80% 미만인 모델은 탈락.
2. 남은 모델 중 Recall@3 차이가 5%p 이내면, **질의 임베딩 지연이 짧은 쪽**을 고른다. CPU 환경에서 체감 속도를 좌우하는 것은 검색이 아니라 임베딩이다.
3. 차원이 작을수록 저장 비용과 검색 비용이 낮다(768 vs 1024). 1, 2가 비기면 작은 쪽.

**Vector DB**
1. FAQ 1,000건 규모에서 두 DB의 검색 지연은 모두 NFR-1.1(500ms)을 크게 밑돌 것이다. **지연으로 결정하지 않는다.**
2. 실제 기준은 **FR-D3(FAQ 변경 시 임베딩 동기화)** 이다.
   - pgvector: 원본과 벡터가 같은 DB에 있어 하나의 트랜잭션으로 묶인다. 실패 시 롤백이 자연스럽다(NFR-2.6).
   - Qdrant: 애플리케이션이 2단계 쓰기를 직접 보정해야 한다. 실패 시 정합성 깨짐(NFR-3.4)을 코드로 막아야 한다.
3. 배포 관점: pgvector 는 인스턴스 1개로 끝난다. Qdrant 는 컨테이너가 하나 더 필요하다(NFR-8.7, AWS 비용).

> 즉 이 실험에서 Qdrant 를 선택할 근거가 되려면 **검색 품질이나 지연에서 유의미한 이점**이 나와야 합니다. 나오지 않으면 pgvector 가 기본값입니다.

## 5. 실행

```bash
docker compose exec api python -m app.ingest      # 6개 조합 적재
docker compose exec api python -m app.evaluate    # 지표 측정
```

결과는 `results/comparison.md`(표 + 실패 사례), `results/comparison.json`, 그리고 Postgres `experiment_run` 테이블에 남습니다.

## 6. 결과 (2026-09-09 실측)

환경: Windows 11 + Docker Desktop, CPU 전용. FAQ 100건, 평가 질문 30건, top-k=5.

### 6.1 종합

| 임베딩 | 차원 | Vector DB | Recall@1 | Recall@3 | Recall@5 | MRR@5 | 검색 평균 | 질의 임베딩 평균 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **bge-m3** | 1024 | pgvector | 76.7% | **90.0%** | 96.7% | 0.841 | 5.6ms | **46ms** |
| **bge-m3** | 1024 | qdrant | 76.7% | **90.0%** | 96.7% | 0.841 | 2.8ms | **46ms** |
| multilingual-e5-large | 1024 | pgvector | 80.0% | 86.7% | 96.7% | 0.858 | 6.0ms | 157ms |
| multilingual-e5-large | 1024 | qdrant | 80.0% | 86.7% | 96.7% | 0.858 | 2.8ms | 157ms |
| nomic-embed-text | 768 | pgvector | 3.3% | 20.0% | 26.7% | 0.113 | 5.6ms | 30ms |
| nomic-embed-text | 768 | qdrant | 3.3% | 20.0% | 26.7% | 0.113 | 2.3ms | 30ms |

같은 벡터를 넣었으므로 **두 DB의 검색 품질 지표는 소수점까지 동일**합니다. 설계대로입니다. DB 비교에서 볼 것은 지연과 운영 방식뿐입니다.

### 6.2 임베딩 모델

**결정: bge-m3**

- nomic-embed-text 는 Recall@3 20.0% 로 판단 기준 1(80% 미만 탈락)에 걸립니다. 한국어에서 쓸 수 없습니다.
- bge-m3(90.0%)와 e5-large(86.7%)의 차이는 3.3%p 로 기준 2의 5%p 이내입니다. 따라서 **질의 임베딩이 3.4배 빠른 bge-m3**(46ms vs 157ms)를 선택합니다.
- e5-large 의 Recall@1 이 3.3%p 높지만(80.0% vs 76.7%), RAG는 top-3를 컨텍스트로 넣으므로 Recall@3 이 더 중요합니다.

**nomic 이 실패한 방식이 특히 중요합니다.**

| | bge-m3 | nomic-embed-text |
| --- | --- | --- |
| 적재 시 유사도 0.95 이상 중복 후보 | **0쌍** | **92쌍** |
| 틀린 검색 결과의 최고 점수 | 0.564 (Q-15) | 0.75 ~ 0.83 |

nomic 은 FAQ 100건을 서로 구분하지 못하고 전부 0.8 언저리로 뭉칩니다. 그래서 **틀린 답에도 높은 점수를 줍니다.**
이 경우 FR-B7(유사도 임계값 미만이면 답변 거부)이 원리적으로 동작하지 않습니다. 어떤 임계값을 잡아도 오답을 걸러낼 수 없기 때문입니다.
NFR-3.3(유사도 0.95 이상 중복 제거)을 nomic 기준으로 돌렸다면 멀쩡한 FAQ 92쌍을 중복으로 오판해 지웠을 것입니다.

> 교훈: 임베딩 모델은 Recall 뿐 아니라 **점수 분포가 변별력을 갖는지**로도 평가해야 합니다. 점수가 신뢰할 수 없으면 임계값 기반 기능이 전부 무너집니다.

### 6.3 Vector DB

**결정: PostgreSQL + pgvector**

| | pgvector | Qdrant |
| --- | --- | --- |
| 검색 품질 | 동일 | 동일 |
| 검색 평균 지연 | 5.6ms | 2.8ms |
| NFR-1.1(500ms) 대비 | 1.1% 사용 | 0.6% 사용 |
| 인덱스 생성(100건) | 16~17ms | 1~3ms |
| FR-D3 동기화 | FAQ 원본과 같은 트랜잭션 | 애플리케이션이 2단계 쓰기 보정 |
| 배포 구성 | 인스턴스 1개 | 컨테이너 1개 추가 |

Qdrant 가 검색은 2배 빠르지만 **절대 차이는 2.8ms** 이고 목표치(500ms)의 1% 수준입니다.
같은 요청 안에서 질의 임베딩이 46ms, LLM 생성이 수 초 걸리는 것을 감안하면 **사용자가 체감할 수 없는 차이**입니다.
판단 기준 2에 따라 FR-D3/NFR-2.6/NFR-3.4 를 트랜잭션으로 해결할 수 있는 pgvector 를 선택합니다.

> Qdrant 로 갈 근거가 되려면 FAQ 1,000건 확장 후에도 지연 차가 여전히 무의미한지 재확인하면 됩니다. 다만 아래 6.3.1 을 먼저 읽으십시오 - 이 규모에서는 두 DB 모두 인덱스를 쓰지 않고 있습니다.


#### 6.3.1 [중요] 이 규모에서는 양쪽 다 ANN 을 쓰지 않는다

두 스토어에 HNSW(m=16, ef_construct=64)를 동일하게 설정했지만, **FAQ 100건에서는 실제로 근사검색이 동작하지 않습니다.** 실행 계획으로 확인한 결과입니다.

| | 설정 | 실제 동작 | 근거 |
| --- | --- | --- | --- |
| pgvector | HNSW 인덱스 생성됨 | **Seq Scan (전수 비교)** | 플래너가 선택. 전수 0.7ms vs 인덱스 강제 시 196ms(JIT 포함) |
| Qdrant | HNSW 설정됨 | **전수 비교** | `indexed_vectors_count: 0`, `indexing_threshold: 20000` |

```bash
# 재현
docker compose exec postgres psql -U raguser -d ragdb -c \
  "EXPLAIN ANALYZE SELECT faq_id FROM faq_vec_bge_m3 ORDER BY embedding <=> (SELECT embedding FROM faq_vec_bge_m3 LIMIT 1) LIMIT 3;"
curl -s http://localhost:6333/collections/faq_bge_m3 | grep -o '"indexed_vectors_count":[0-9]*'
```

**따라서 6.1 표의 검색 지연(5.6ms vs 2.8ms)은 ANN 성능 차가 아니라 두 엔진의 전수 비교 구현 차이입니다.**

이것이 결론에 주는 영향:

- Vector DB 선택 결론(pgvector)은 **바뀌지 않습니다.** 오히려 강화됩니다. 두 DB 모두 인덱스 없이 전수 비교로 목표(500ms)의 1% 안에 들어오므로, 검색 성능은 선택 기준이 될 수 없습니다.
- **본 프로젝트 목표인 FAQ 1,000건도 Qdrant 의 기본 임계값 20,000 미만입니다.** 1,000건에서도 Qdrant 는 전수 검색을 합니다. 즉 이 프로젝트 규모에서 HNSW 파라미터 튜닝은 논의할 필요가 없습니다.
- 1,000건 x 1024차원 전수 비교는 약 100만 회 부동소수 연산으로, 수 ms 수준입니다. 100건 결과에서 10배 늘어나도 NFR-1.1(500ms)에 한참 못 미칩니다.
- ANN 이 의미를 갖는 시점은 대략 수만 건부터입니다. 그 전까지 "인덱스를 뭘 쓸까"는 실제 문제가 아닙니다.

#### 6.3.2 규모별 실측 (합성 벡터 1024차원, `app/scale_bench.py`)

| 건수 | 스토어 | 적재 | 인덱스 | 검색 평균 | 검색 p95 | 저장 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 | pgvector | 0.3s | 0.3s | 6.0ms | 6.5ms | 13.3MB |
| 1,000 | qdrant | 1.1s | 0.0s | **3.6ms** | 3.8ms | - |
| 10,000 | pgvector | 3.1s | 5.5s | 8.9ms | 9.6ms | 131.8MB |
| 10,000 | qdrant | 3.2s | 0.0s | **3.9ms** | 4.2ms | - |

컨테이너 유휴 메모리 (10,000건 적재 후): **Qdrant 151MB, Postgres 187MB.**

**Qdrant 는 이 규모에서 무겁지 않습니다. 오히려 Postgres 보다 가볍고 검색도 2배 빠릅니다.**
1,000건은 두 DB 모두 NFR-1.1(500ms)의 1% 남짓만 씁니다. 10,000건까지 늘려도 마찬가지입니다.
pgvector 는 건수에 따라 지연이 증가하고(6.0 → 8.9ms) Qdrant 는 거의 평평하지만, 절대값이 한 자릿수 ms 라 의미가 없습니다.

**그래도 pgvector 를 고르는 이유는 성능이 아니라 6.3 의 FR-D3 동기화 책임 때문입니다.**
"Qdrant 가 무거워서 뺀다"는 근거는 틀렸습니다. 그렇게 설명하지 마십시오.
### 6.4 top-k 와 유사도 임계값

- **top-k = 3 으로 시작**합니다. Recall@3 90.0%, Recall@5 96.7% 로 5가 더 정확하지만, CPU LLM 은 컨텍스트가 길수록 첫 토큰이 느려집니다(NFR-1.3). 답변 품질이 부족하면 4~5로 올려 재측정하세요.
- **유사도 임계값(FR-B7)**: bge-m3 기준 현재 `SIM_THRESHOLD=0.45` 로 두었습니다. 유일한 검색 실패(Q-15, 0.564)가 임계값을 넘겨 통과하므로, 이 값은 "FAQ에 아예 없는 질문"을 거르는 용도이지 오검색을 막지는 못합니다. FAQ 1,000건으로 확장한 뒤 정답/오답 점수 분포를 다시 그려 조정해야 합니다.

### 6.5 LLM 응답 시간 (CPU, exaone3.5:7.8b)

`app/llm_bench.py` 로 같은 질문 5건을 두 번 측정했습니다. **세 가지 상태를 구분해야 합니다.**

| 상태 | 첫 토큰 | 전체 | NFR-1.3 (3초) | NFR-1.4 (15초) |
| --- | ---: | ---: | --- | --- |
| ① 콜드 스타트 (모델 최초 로딩 포함, 1건) | 15.6s | 25.0s | **미달** | **미달** |
| ② 모델 로딩 후 · 새로운 질문 (4건 평균) | **3.0s** | **11.2s** | 경계 | **충족** |
| ③ 재실행 (동일 프롬프트, 프롬프트 캐시 적중) | 0.2s | 8.8s | 충족 | 충족 |

**계획에 쓸 숫자는 ②입니다.** ③은 Ollama 가 직전과 같은 프롬프트의 KV 캐시를 재사용해 나온 값이라 실사용을 대표하지 않습니다.
①은 `OLLAMA_KEEP_ALIVE` 안에 요청이 계속 들어오면 한 번만 발생합니다(compose 에 10분으로 설정해 두었습니다).

②의 개별 측정값:

| 질문 | 첫 토큰 | 전체 | 근거 FAQ |
| --- | ---: | ---: | --- |
| 약정 1년쯤 지났는데 지금 해지하면 얼마 물어내요? | 3.4s | 11.8s | FAQ-043, 076, 029 |
| 일본 가는데 데이터 어떻게 써요? | 2.9s | 12.2s | FAQ-032, 098, 074 |
| 애들 이름으로 폰 만들려면 뭐 챙겨가요? | 3.0s | 12.0s | FAQ-003, 048, 036 |
| 해지 매장 안 가고 집에서 되나요? | 2.6s | 8.6s | FAQ-051, 041, 042 |

한 요청의 시간 구성은 **임베딩 50ms + 검색 9ms + LLM 생성 8~12초** 입니다.
검색 계층 최적화는 의미가 없고, **체감 속도는 전적으로 LLM이 결정합니다.** 그래서 SSE 스트리밍(첫 토큰 3초)이 필수입니다.

**답변 품질**: 5건 모두 정책 문서와 일치했고 없는 숫자를 지어내지 않았습니다.
"약정 1년" 질문에는 "정확한 기간에 따라 다르다"며 35% 구간을 제시하고 고객센터를 안내했습니다 — FR-B11(되묻기)에 가까운 바람직한 동작입니다.

> **6.4항 A/B/C 결정에 대한 시사점**
> ② 기준으로 CPU 환경에서도 NFR-1.4(15초)는 충족하고 NFR-1.3(3초)은 경계선입니다.
> 즉 **A안(EC2에 Ollama 동시 탑재)이 성능만으로 배제되지는 않습니다.** 다만 이 수치는 개발용 PC 기준이고,
> EC2 CPU 인스턴스는 코어 수와 메모리 대역폭이 낮아 2~3배 느려질 수 있습니다. A안을 검토한다면
> **대상 인스턴스 타입에서 이 벤치마크를 그대로 한 번 돌려 보고** 결정하십시오. `app/llm_bench.py` 가 그 용도입니다.
> 그리고 동시 사용자 10명(NFR-1.5)은 별개 문제입니다. Ollama 는 기본 순차 처리라 10명이면 대기가 누적됩니다.

| 모델 | 상태 | 첫 토큰 | 전체 |
| --- | --- | ---: | ---: |
| exaone3.5:7.8b | ② 워밍 | 3.0s | 11.2s |

> 2.4b 측정은 `docker compose exec ollama ollama pull exaone3.5:2.4b` 후
> `docker compose exec api python -m app.llm_bench --model exaone3.5:2.4b` 로 채우면 됩니다.
